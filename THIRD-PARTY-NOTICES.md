# Redistributed native libraries

Provenance below is pinned by git blob hash against upstream history, not by filename, so each entry
names the exact upstream revision the shipped binary came from.

## UniDec / IsoDec — `isodeclib.dll`, `isogenmass.dll`

- **Publisher:** Marty Lab, University of Arizona — Michael T. Marty
- **Copyright:** 2016 University of Oxford; 2017-2025 Arizona Board of Regents on behalf of the
  University of Arizona
- **Source:** https://github.com/michaelmarty/UniDec
- **Pinned revision:** upstream commit
  [`3fec24bf`](https://github.com/michaelmarty/UniDec/commit/3fec24bf) (2024-11-15). Both binaries
  match that commit byte for byte: `isodeclib.dll` is blob `a89f4ad9648f…` and `isogenmass.dll` is blob
  `072d3f72d33e…`, each identical to `unidec/IsoDec/` at that revision. They came from upstream
  directly, not from a fork.
- **Licence:** BSD 3-Clause, plus a fourth clause requiring citation (quoted below)
- **Redistributed in:** the mzLib NuGet package, copied from `MassSpectrometry/` into consumers' output
  directories. Loaded by P/Invoke from
  `MassSpectrometry/Deconvolution/Algorithms/IsoDecAlgorithm.cs`, reached only when
  `DeconvolutionType` is `IsoDecDeconvolution`.
- **Added in:** mzLib #791, 2025-01-10

**The fourth clause binds anything that redistributes these binaries, mzLib and its consumers
included:**

> 4. Any publications that result from use of the software should cite Marty et al. Anal. Chem. 2015.
>    DOI: 10.1021/acs.analchem.5b00140. If UniDec is redistributed or incorporated into other
>    software, it must be clearly indicated to the end user that UniDec is being used, and the request
>    to cite Marty et al. Anal. Chem. 2015. DOI: 10.1021/acs.analchem.5b00140 must be passed on to the
>    end user.

So a consumer exposing IsoDec deconvolution must tell its own users UniDec is in use and pass the
citation request on. MetaMorpheus discharges this by writing the citation into
`AutoGeneratedManuscriptProse.txt` whenever a task ran with IsoDec selected.

Full licence text: https://github.com/michaelmarty/UniDec/blob/master/LICENSE

**Both binaries are stale, and updating them is a migration rather than a swap.** Upstream has revised
`isodeclib.dll` nine times since (through 2025-10-15), and **removed `isogenmass.dll` entirely** in
June 2025, consolidating that functionality into an `isogen` target whose exported names differ
(`isogenmass_nn`, declared in `isogendep.h`). A future update therefore needs the P/Invoke signatures
revisited, not just the files replaced.

## Bruker — `timsdata.dll`, `timsdata.lib`, `baf2sql_c.dll`, `baf2sql_c.lib`

- **Publisher:** Bruker Daltonics
- **Licence:** proprietary, distributed with Bruker's timsTOF/BAF SDKs. **The terms are not reproduced
  anywhere in this repository**, so what they permit has not been established here and no claim is made
  about it. This is the largest remaining gap in this file.
- **Redistributed in:** the mzLib NuGet package, from `Readers/`. Loaded by P/Invoke from
  `Readers/timsTOF/TimsTofFileReader.cs` (15 imports) and `Readers/Bruker/BrukerFileReader.cs`
  (9 imports).
- **Added in:** `baf2sql_c.*` in mzLib #702, 2023-05-16; `timsdata.*` in mzLib #812, 2025-01-19
- **Platforms:** Windows x86-64 only. Bruker publishes Windows and Linux x86-64 builds and no macOS
  build at all; see smith-chem-wisc/mzLib#1158.

**Action needed:** obtain the applicable Bruker SDK licence and record whether NuGet redistribution is
permitted and on what conditions. Until then this entry documents the gap rather than closing it.

## Microsoft Visual C++ 2012 runtime — `msvcp110.dll`, `msvcr110.dll`, `vcomp110.dll`

- **Publisher:** Microsoft
- **Why present:** dependencies of the Bruker libraries above, not used directly by mzLib. They
  arrived in the same commit as `baf2sql_c.dll` (mzLib #702, 2023-05-16).
- **Licence:** the Visual C++ 2012 redistributable terms, which are Microsoft's and are not reproduced
  here. Microsoft permits redistribution of the runtime's redistributable components under those terms;
  the specific version and conditions have not been verified for this file.

**Action needed:** confirm these are the redistributable components rather than the SDK-only copies, and
record the applicable terms. Shipping loose `msvc*110.dll` files beside an application is also worth
revisiting on its own merits — the supported route is the redistributable package.

## Intel compiler runtime — `libmmd.dll`, `svml_dispmd.dll`

- **Publisher:** Intel
- **Why present:** dependencies of `isodeclib.dll`, which is evidently built with the Intel C compiler.
  They arrived in the same commit as IsoDec itself (mzLib #791, 2025-01-10) and are used by nothing in
  mzLib directly.
- **Licence:** Intel's redistributable terms, which are **not reproduced in this repository**, so no
  claim is made about what they permit.
- **Origin not established:** UniDec bundles files of the same names under `unidec/bin/`, but the copies
  here are **not** byte-identical to UniDec's at the pinned revision `3fec24bf`, nor to its current ones.
  So unlike `isodeclib.dll` these cannot be traced to an upstream commit, and may have come from an
  Intel compiler or oneAPI installation directly.

**Action needed:** establish where these came from and under which Intel redistribution terms.

Worth noting for anyone revisiting this: they are an artifact of *how* IsoDec was compiled rather than
of what it needs. A GCC or Clang build of the same sources links only FFTW and the system math library
— confirmed by building IsoDec from source on macOS arm64, which produces no Intel runtime dependency
at all. Building the natives per platform, as smith-chem-wisc/mzLib#1158 discusses, would retire these
two files rather than needing macOS and Linux equivalents of them.
